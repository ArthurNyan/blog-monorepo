# Детализированный План C Для Усиления Приложения И Диплома

Дата актуализации: `2026-05-22`.

## Назначение

Этот документ фиксирует один рабочий сценарий: `План C`, в котором сначала
последовательно усиливается само приложение как инженерная система, а затем под это
состояние синхронизируется диплом.

Документ нужен для двух целей:

- передавать отдельные этапы агентам без потери контекста;
- по завершении всех этапов получить не только улучшенный проект, но и
  обновляемый, защищаемый текст ВКР.

## Принцип Плана C

В рамках этого плана делаются только такие изменения, которые можно потом описать в дипломе как:

- новый архитектурный контур;
- новая подсистема;
- новая редакторская возможность;
- новая эксплуатационная схема;
- новая модель безопасности;
- новый контур проверки и доказательства результата.

Следующие задачи не приоритетны и не должны отъедать время, если они не влияют на ВКР:

- мелкие рефакторинги ради чистоты кода;
- локальная дедупликация функций;
- незначительные UI-полировки;
- “улучшение архитектуры” без нового защищаемого результата;
- абстрактная оптимизация кода, которую потом нельзя объяснить в главе 2.

## Итог, К Которому Должен Привести План

После завершения всех этапов в репозитории должно быть:

- рабочее приложение с оформленным `publish -> webhook -> rebuild` контуром;
- versioned deployment-контур для `Astro` и `Strapi`;
- согласованная мультиязычная модель `ru/en` для ключевых публичных сущностей;
- единый CMS-managed `SEO/Open Graph` контур;
- формализованные `roles/permissions` и редакторский workflow;
- воспроизводимая матрица проверки, включая preview, `SEO`, `sitemap`, `ru/en`,
  публикацию, доступность и базовую производительность;
- обновленный диплом, в котором главы, заключение и приложения синхронизированы
  с фактическим состоянием проекта.

## Общие Правила Для Любого Агентного Этапа

Каждый агент, который берет отдельный этап, должен:

1. Сначала изучить текущий код и `thesis/knowledge/diploma/*`.
2. Не выдавать план за реализованный результат.
3. Явно фиксировать:
   - что реализовано;
   - что проверено;
   - что осталось ограничением;
   - что именно нужно будет отразить в дипломе.
4. После технических изменений обновлять `knowledge`, чтобы следующий этап
   опирался уже на новый baseline.
5. Не тратить время на локальные рефакторинги, если они не усиливают ВКР.

## Последовательность Этапов

Этапы нужно выполнять по порядку:

1. `Этап 0` — зафиксировать baseline и целевой scope.
2. `Этап 1` — publication and deployment core.
3. `Этап 2` — полный `ru/en` public contour.
4. `Этап 3` — единый CMS-managed `SEO/Open Graph`.
5. `Этап 4` — `roles/permissions` и editor workflow.
6. `Этап 5` — testing, metrics, acceptance evidence.
7. `Этап 6` — дипломные артефакты: схемы, таблицы, приложения, evidence pack.
8. `Этап 7` — переписывание текста ВКР под реальное финальное состояние.
9. `Этап 8` — финальная синхронизация проекта и диплома перед защитой.

Если какой-то этап не закрыт, следующий не должен маскировать этот разрыв.

## Этап 0. Baseline И Фиксация Scope

### Цель

Перед началом интеграций зафиксировать:

- что уже есть в проекте;
- что считается обязательным финальным результатом;
- какие именно формулировки допустимы в дипломе после будущих доработок.

### Почему это усиливает диплом

Без этого этапа следующие агенты легко начнут:

- делать лишнюю работу;
- реализовывать противоречащие друг другу решения;
- писать в `knowledge` разные версии scope;
- плодить расхождение между проектом и будущим текстом диплома.

### Что должно появиться в репозитории

- обновленный baseline в `thesis/knowledge/diploma/*`;
- явный список финального scope:
  - какие разделы должны войти в общий `ru/en`;
  - какие сущности получают полноценный SEO-контур;
  - какие роли считаются обязательными;
  - что именно будет входить в acceptance/testing;
- короткий файл или раздел с `final-claim boundaries`, который потом можно использовать
  при переписывании введения и заключения.

### Что потом появится в дипломе

- более точные цель и задачи;
- отсутствие завышенных обещаний;
- четкая граница между “входит в результат” и “остается вне объема”.

### Критерий завершения этапа

- существует единый, зафиксированный финальный scope;
- все последующие этапы могут опираться на него без повторного переопределения темы.

### Артефакты для защиты

- обновленные `knowledge`-файлы;
- список финальных claims, которые будет допустимо произносить на защите.

## Этап 1. Publication And Deployment Core

### Цель

Замкнуть эксплуатационный контур системы:

- `Strapi publish -> webhook -> rebuild frontend`;
- versioned deployment-конфигурация для CMS;
- зафиксированный env-contract для production-like использования.

### Почему это усиливает диплом

Это переводит работу из состояния “есть CMS и витрина” в состояние
“есть воспроизводимый публикационный процесс”.

Именно здесь появляется один из самых сильных защищаемых тезисов:

- редакторская публикация не требует ручного вмешательства разработчика в frontend.

### Что должно появиться в проекте

- оформленный `webhook -> rebuild` сценарий;
- versioned deployment files для `apps/cms` в `Docker`;
- понятный набор env-переменных для preview, public URLs, rebuild hook и production-like запуска;
- обновленная knowledge-документация по deployment и publication flow.

### Что потом появится в дипломе

- подраздел про публикационный контур;
- подраздел про deployment-архитектуру;
- схема `Strapi -> publish -> webhook -> rebuild -> Astro/Vercel`.

### Критерий завершения этапа

- rebuild вызывается через оформленный механизм;
- CMS поднимается через versioned `Docker`-контур;
- ограничения и проверенные сценарии явно зафиксированы.

### Артефакты для защиты

- deployment-схема;
- env-contract таблица;
- сценарий публикации;
- подтверждение того, что rebuild запускается без ручного `frontend build`.

### Фактический статус после закрытия publication/deployment contour

Зафиксировано как реализованный результат:

- versioned admin-managed webhook `Strapi entry.publish/entry.unpublish -> rebuild hook`;
- versioned Docker contour `apps/cms`;
- отдельный env-contract для preview, rebuild hook и Docker deployment;
- материалы для главы 2 по publication flow и deployment architecture.

Локально доказано:

- `TypeScript`-компиляция и production build CMS;
- создание webhook-записи в `strapi_webhooks` при старте CMS;
- валидность `compose.yml` при корректном `.env.docker`.

Не доказано как end-to-end локальный факт:

- внешний `Vercel` rebuild после production hook;
- полный `docker build`, если он срывается внешней сетью/registry path, а не ошибкой bundle.

## Этап 2. Полный Публичный Контур `ru/en`

### Цель

Довести мультиязычность до состояния, которое можно защищать как свойство платформы,
а не как частичную особенность storefront первой очереди.

### Почему это усиливает диплом

Сейчас `ru/en` уже есть на части маршрутов, но для сильной главы 2 этого мало.
После этапа можно писать, что система обеспечивает двуязычную модель не только
для маркетинговых страниц, но и для ключевых публичных сущностей.

### Что должно появиться в проекте

- согласованный locale-aware public contour для `articles` и `projects`;
- принятое и зафиксированное решение по `vacancies`:
  - либо включение в общий `ru/en`;
  - либо документированное ограничение;
- согласованные localized links, canonical rules, route rules и fallback behavior;
- обновленная knowledge-документация по i18n-модели.

### Что потом появится в дипломе

- отдельный подраздел по мультиязычной архитектуре;
- таблица “CMS locale -> public locale -> route pattern”;
- более сильная практическая значимость для контент-менеджера.

### Критерий завершения этапа

- `home-page`, `pages`, `articles`, `projects` работают в согласованной `ru/en` модели;
- решение по `vacancies` зафиксировано и непротиворечиво;
- sitemap/canonical logic не ломается на новых маршрутах.

### Артефакты для защиты

- матрица публичных маршрутов;
- таблица локалей;
- скриншоты `ru/en` версий;
- формулировка ограничений, если `vacancies` остаются в частичном scope.

### Фактический статус после закрытия multilingual contour

Зафиксировано как реализованный результат:

- трехслойная locale model `site locale (ru/en) -> CMS locale (ru-RU/en) -> public route pattern`;
- locale-prefixed production routes для `home-page`, `page`, `articles`, `projects`;
- locale-aware preview для `home-page`, `page`, `article`, `project`, `vacancy`;
- locale-aware links и route helpers на стороне frontend;
- redirect compatibility для legacy `/articles/*` и `/projects/*`;
- исключение legacy `articles/projects` маршрутов из `sitemap`, чтобы не плодить дубли;
- осознанное ограничение по `vacancies`: locale-ready CMS и preview без полного
  двуязычного production-контура карьерного UI.

Локально доказано:

- `articles` и `projects` строятся по `/:locale/articles/...` и `/:locale/projects/...`;
- preview для `article/project` возвращает на новые locale-aware public URLs;
- `canonical` строится от новых locale-prefixed path helpers;
- `sitemap` фильтрует legacy redirect routes и оставляет индексируемыми только финальные
  public URLs.

Не следует заявлять как реализованный результат:

- двуязычный `VacancyExplorer` и форма отклика;
- полный locale-prefixed production contour для `vacancies`;
- единый editor-managed `SEO` schema для всех content sections.

## Этап 4. `Roles/Permissions` И Editor Workflow

### Цель

Оформить редакторскую безопасность и публикационный workflow как самостоятельную часть системы.

### Почему это усиливает диплом

Это превращает работу из “CMS как хранилище контента” в “CMS как управляемую редакторскую платформу”.

Комиссия почти всегда позитивно воспринимает именно такие вещи:

- кто имеет доступ;
- кто публикует;
- кто видит отклики;
- как ограничен preview;
- где заканчивается public API и начинается административный контур.

### Что должно появиться в проекте

- минимальный набор ролей;
- матрица прав по сущностям и действиям;
- воспроизводимое или максимально формализованное описание настройки прав;
- knowledge-документация по editor workflow и security boundaries.

### Что потом появится в дипломе

- отдельный подраздел по ролям и правам;
- подраздел по защите редакторского и публичного контура;
- матрица прав в приложении или в основной главе 2.

### Критерий завершения этапа

- роли и права не являются больше “подразумеваемой идеей”;
- границы доступа формализованы и могут быть показаны без устных пояснений.

### Артефакты для защиты

- матрица ролей и действий;
- описание preview access model;
- описание public/private boundaries.
